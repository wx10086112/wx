# 门店管理第二阶段实施方案

## 1. 文档目标

第一阶段只保证每个商家拥有并管理一家主门店。第二阶段目标是完整支持多门店，但必须同步打通消费者选店、商品适用门店、下单门店归属、预约、核销和商家员工门店权限，不能只增加后台分店按钮。

## 2. 第一阶段边界

- 新增商家自动创建第一家主门店。
- 历史商家可在商家详情创建第一家主门店。
- 已有主门店可以编辑或停用。
- 暂不支持新增分店、删除门店、切换主门店。
- 商品、订单、预约、核销和商家端流程保持不变。

## 3. 第二阶段必须解决的现有冲突

### 3.1 消费者端选店

当前 C 端首页只取主门店或查询结果中的第一家门店。第二阶段需要增加门店列表与选店状态，并明确以下规则：

- 首次进入默认选择主门店。
- 用户手动选择后在本地保存 `storeId`。
- 商家切换、门店停用或门店被移除时清理失效选择。
- 首页、门店详情、商品列表、购物车和结算页使用同一 `storeId`。

### 3.2 商品适用门店

`product.store_ids` 和团购项目 `store_ids` 已存在，但当前 C 端没有完整使用。需要统一定义：

- 空值代表全部有效门店可用，或强制显式选择，二者只能选一种规则。
- 后台商品编辑增加适用门店选择器。
- 商品列表和详情接口按当前 `storeId` 过滤。
- 商品状态变更、门店停用后重新校验购物车。

建议采用“空值代表全部营业门店可用”，兼容现有商品数据。

### 3.3 下单与订单归属

当前结算请求没有提交 `storeId`。第二阶段必须：

1. 结算页显示并确认当前门店。
2. 创建订单请求提交 `storeId`。
3. 后端校验门店存在、营业、属于当前 AppID 对应商家。
4. 后端校验全部商品适用于该门店。
5. `mall_order.store_id` 必须由后端验证后写入，不能只相信前端。
6. 购物车禁止混合不同商家或不同门店商品。

### 3.4 预约与核销

- 创建预约时写入并校验 `booking_record.store_id`。
- 核销时校验员工所属门店、订单门店和核销门店是否匹配。
- 店主可查看全部门店，普通员工默认只能处理所属门店。
- 历史 `store_id` 为空的数据继续按商家级记录展示，不做错误归属。

### 3.5 商家员工门店权限

`merchant_user` 已包含门店关联能力时，应在员工管理中提供所属门店选择；若字段不足，再增加明确的关联表。规则如下：

- 店主可以不绑定单店，代表管理全部门店。
- 普通员工必须绑定一个有效门店。
- 门店停用时员工仍保留关系，但不可处理新业务。
- 门店移除前必须先处理员工、商品和未完成订单关联。

### 3.6 主门店唯一性

数据库当前没有保证一个商家只有一个主门店。服务层需要在事务中执行：

1. 锁定该商家的有效门店记录。
2. 清除旧主门店标记。
3. 将目标门店设为主门店。
4. 校验最终只有一条 `is_main = 1`。

上线前需要扫描并修复“无主门店”和“多个主门店”的历史数据。不要直接增加会因脏数据失败的唯一索引。

## 4. 后台管理能力

商家详情的“门店信息”页签升级为门店列表，提供：

- 新增分店。
- 编辑门店。
- 启用或停用。
- 设置主门店。
- 查看关联商品、员工、未完成订单数量。

第二阶段仍不建议物理删除。需要移除时使用软删除，并满足：

- 不能移除唯一门店。
- 不能移除当前主门店，必须先切换主门店。
- 不能存在未完成订单、有效预约或未处理售后。
- 商品和员工关联必须先迁移或解除。

## 5. 建议接口

```text
GET    /mall/merchant/{merchantId}/stores
POST   /mall/merchant/{merchantId}/stores
PUT    /mall/merchant/{merchantId}/stores/{storeId}
PUT    /mall/merchant/{merchantId}/stores/{storeId}/status
PUT    /mall/merchant/{merchantId}/stores/{storeId}/main
GET    /wxmini/merchant/stores
PUT    /wxmini/user/current-store
```

所有管理接口继续执行商家归属和分销商数据范围校验。C 端接口按 `X-Wx-AppId` 识别商家，不能接受跨商家的 `storeId`。

## 6. 数据迁移

上线前执行只读检查：

```sql
SELECT merchant_id, COUNT(*) AS store_count,
       SUM(CASE WHEN is_main = 1 THEN 1 ELSE 0 END) AS main_count
FROM merchant_store
WHERE del_flag = '0'
GROUP BY merchant_id;
```

迁移步骤：

1. 为无门店商家补建主门店，资料来自 `merchant`。
2. 为有门店但无主门店的商家选择最早有效门店为主门店。
3. 多主门店只保留最早一条为主门店。
4. 回填 `merchant.store_count`。
5. 保留历史订单的原 `store_id`，不重新猜测归属。

## 7. 推荐实施顺序

1. 后端门店列表、主门店事务和数据校验。
2. 后台多门店管理与商品适用门店配置。
3. C 端选店和统一门店状态。
4. 商品列表、详情和购物车按门店过滤。
5. 下单请求与后端订单门店校验。
6. 预约、核销和员工门店权限。
7. 历史数据迁移和灰度发布。

## 8. 测试范围

- 一个商家只能有一个主门店。
- 分销商不能操作其他分销商商家门店。
- 停用门店不接受新订单和预约。
- 商品不适用于当前门店时无法加入购物车或下单。
- 跨商家、跨门店篡改 `storeId` 被后端拒绝。
- 普通员工不能核销其他门店订单。
- 主门店切换后首页默认门店正确，历史订单不变。
- 旧订单 `store_id` 为空时仍可查询和退款。

## 9. 上线与回滚

- 先部署兼容旧请求的后端，再发布后台，最后发布小程序。
- 后端在小程序新版本覆盖前允许旧下单请求不传 `storeId`，但只可落到唯一主门店。
- 观察订单门店归属、预约和核销指标后再强制 `storeId`。
- 回滚时只关闭多门店入口和选店功能，不删除已创建门店及历史关联数据。

## 10. 验收标准

- 商家可以管理多个门店且始终只有一个主门店。
- 用户能明确选择门店，商品、购物车、结算和订单保持同一门店。
- 订单、预约、核销和员工权限均能追溯到正确门店。
- 停用或移除门店不会破坏历史订单、退款和财务记录。
- 平台管理员、分销商和商家员工的数据范围均符合现有权限模型。
