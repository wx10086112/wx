# 一个商家一个小程序的接入改造记录

这几天把手上的一个多端商家项目往前推进了一大步。

它不是一个单纯的商城小程序，而是一套带有 **C 端用户小程序、B 端商家履约端、运营后台、后端服务** 的完整系统。最开始项目里有一些历史包袱，比如商家端前端目录是独立的，微信配置是半静态的，后台能录入商家参数，但还不够“直接拿去接商家用”。

这次改造的目标很明确：

> 让系统真正支持“一个商家一个小程序主体、一个商家一套接入参数”，并且让商家能实际通过后台配置和入口码跑起来。

这篇文章就把这次改造里几个关键节点记下来。

## 一、项目原来的状态

项目整体结构大概是这样：

- `wx_app`：小程序前端
- `ruoyi-vue-wxmini-main/ruoyi-ui`：运营后台
- `ruoyi-vue-wxmini-main/ruoyi-admin`：后端启动模块
- `ruoyi-vue-wxmini-main/ruoyi-wxmini`：小程序相关接口
- `ruoyi-vue-wxmini-main/ruoyi-mall-*`：商品、订单、商家、财务等业务模块

最初看下来，系统已经有了不少基础能力：

- C 端和 B 端页面都已经有了
- 商家后台也已经有商家管理、员工管理、订单、财务这些页面
- 后端也已经按模块拆开

但真正要落到“可交付商家接入”这件事上，还有几个现实问题：

1. B 端虽然存在，但历史上是独立目录，后面其实已经并入 `wx_app` 了。
2. 商家可以在后台配置 `AppID/Secret`，但这套配置没有真正形成完整接入闭环。
3. `AppID` 没有做唯一性兜底，理论上会出现串商家的风险。
4. 改完商家的 `Secret` 后，运行中的微信服务缓存不会自动刷新。
5. 商家怎么进入 B 端，入口并不够稳定清晰。

说白了，系统“能演示”，但还没到“敢直接拿去对接商家”的程度。

## 二、B 端不再独立，直接并入统一小程序

这次我先做的一件事，是把项目结构口径统一下来。

原来仓库里既有 `wx_app`，又保留了一个历史的 `merchant_app`。实际梳理后发现，商家端页面已经基本都并到 `wx_app/pages/merchant/*` 下面了，继续保留旧目录只会让维护越来越混乱。

所以最后定下来的方向是：

- C 端页面继续在 `wx_app/pages/*`
- B 端页面统一在 `wx_app/pages/merchant/*`
- `merchant_app` 只作为历史备份，不再作为正式入口

这个决定其实很重要，因为它影响后面很多东西：

- B 端登录入口怎么做
- 小程序二维码跳哪里
- 商家端接口怎么识别当前商家
- 文档怎么写

统一之后，思路就清楚很多了：**一个小程序里同时承载 C 端和 B 端页面，B 端通过专属入口页进入。**

## 三、真正关键的点，不是页面，而是商家接入模型

这次最核心的业务判断其实不是技术，而是接入模式。

最后确定的模式是：

> 每个商家自己有一个小程序主体和自己的 AppID，我们的平台后台负责录入接入参数并提供后续业务能力。

这和“所有商家共用一个总小程序”是两种完全不同的架构。

一旦明确成“一个商家一个小程序”，很多问题反而简单了：

- 商家归属可以直接依赖 `AppID`
- B 端入口二维码不一定需要再额外塞复杂参数
- 后端可以根据 `AppID` 动态切换当前商家上下文

但同时也对后台提出了更高要求：

- 商家的 `AppID/Secret` 必须录得准
- `AppID` 不能重复
- 改完配置必须立即生效

否则商家越多，系统越容易乱。

## 四、把商家 AppID/Secret 真正接到后端里

这部分是这次改造里最像“补齐地基”的工作。

我主要做了三件事。

### 1. 给商家小程序配置做成对校验

以前后台表单虽然能填 `AppID` 和 `Secret`，但没有严格保证它们成对出现。

这次改完后，新增和编辑商家时都会检查：

- `C 端 AppID` 和 `C 端 Secret` 必须同时填写或同时为空
- `商家端 AppID` 和 `商家端 Secret` 必须同时填写或同时为空

这样可以避免最常见的配置错误：只填了一个值，保存了，但运行时才报错。

### 2. 给 AppID 增加唯一性校验

这是我觉得必须补的一项。

因为系统内部是按 `AppID -> 商家` 来识别归属的，如果两个商家配了同一个 `AppID`，后面登录、取商家信息、下发微信能力时都会出问题。

这次既加了接口层校验，也补了数据库唯一索引脚本：

- `09_merchant_miniapp_unique_indexes.sql`

这样就不只是“前端别填错”，而是数据库层也兜住了。

### 3. 支持 Secret 改完后动态刷新

原来还有一个很隐蔽的问题：

后台就算改了商家的 `Secret`，运行中的服务也不会自动刷新，得重启才生效。

这个在开发阶段可能还好，在线上就很难受，因为你明明改对了参数，但前台还是报登录失败。

这次我把微信服务管理做成了 `registerOrRefresh` 模式，后台保存商家配置后，直接同步刷新缓存，不用再靠手工重启后端。

这一步做完之后，“商家自带 AppID/Secret 接入”才真正从静态配置升级成了可运维能力。

## 五、商家怎么进 B 端，最后落到了“入口码”

项目做到这里，另一个很现实的问题出现了：

> 商家知道怎么进入自己的 B 端吗？

答案是，不能靠“你自己想办法找到一个页面路径”。

真正能落地的还是入口码。

这个项目里最后采用的是：

- 后台商家详情页生成“商家后台入口码”
- 店长或员工扫码后直接进入 `/pages/merchant/login/login`
- 并通过 `merchantId` 进入对应商家的登录上下文

这个思路比把入口藏在 C 端首页里靠谱很多，因为它更接近真实使用方式：

- 后台生成码
- 发给商家
- 商家扫码
- 进入 B 端登录页

而不是要求每个商家自己记页面路径。

后来实际联调时还发现了一个小问题：

- 页面上入口路径文案有时会显示成 `merchantId=undefined`

本质原因不是后端没做，而是前端详情页初次渲染时用了还没回来的 `merchant.id`。这个问题不大，但非常影响观感，所以也顺手修了，统一改成优先使用后端返回的登录页路径，回退时再用路由中的 `merchantId`。

## 六、这类项目最容易卡住的，往往不是代码本身

这次上线前后还踩了几个特别典型的坑。

### 1. 后端启动正常，不代表后台页面已经同步

一开始我只发了后端 `jar` 到服务器，结果服务是起来了，但后台页面里我刚修的入口码区域根本看不到。

后来才确认：

- 后端是 `/opt/ruoyi-xm/ruoyi-admin.jar`
- 后台前端是单独由 `nginx` 托管在 `/var/www/ruoyi-xm-admin`

也就是说：

> Java 后端和 Vue 后台是两套独立部署物。

这个在多人项目里特别容易被忽略。后端改了不等于前端也改了，尤其是运营后台这种独立构建的 Web 项目。

### 2. 编译通过，不等于产物一定是干净的

这次还遇到了一个比较诡异的问题：本地打包能过，但服务器启动时却报 `ClassNotFoundException: WxMerchantItemDto`。

最后查出来不是服务器单独坏了，而是本地某个旧的编译产物里混进了坏 class。

真正解决办法不是继续猜，而是：

- 回到真实项目目录
- 做完整 `clean package`
- 重新检查产物
- 再部署

这也算一个提醒：**对多模块项目来说，增量编译和历史产物有时候比源码本身更危险。**

### 3. GitHub 贡献不亮，有时候不是没推上去

这次推送后，我还顺手把提交作者信息改了一次。

原因很简单：第一次提交作者是本地工具默认身份，不是我的 GitHub 邮箱，所以贡献图不会亮。

后来把仓库的提交身份改成自己的 GitHub 绑定邮箱，再重写最近一次提交并强推，贡献才会被 GitHub 正常归档。

这虽然和业务无关，但也属于项目收尾时很容易忽略的小细节。

## 七、这次改造之后，项目更像一个“能接商家”的系统了

如果只看页面，这次改动不算最夸张。

但如果从“能不能真的接一个商家来用”这个标准看，它已经往前走了一大步。

现在这套系统至少已经具备了这些更实用的特征：

- B/C 端结构统一，不再分裂
- 商家可配置自己的小程序参数
- `AppID` 唯一性有校验和数据库兜底
- 改 `Secret` 后可以热刷新
- 后台能生成商家后台入口码
- 线上部署时后端和后台前端的边界更清楚了

当然，这还不是终点。

后面如果继续往生产方向推进，至少还有几件事要补：

1. 商家员工登录体系继续收口，彻底摆脱 mock 逻辑。
2. 微信支付、退款、分账、结算闭环继续补完。
3. 后台对商家配置的引导再做细一些，降低一线运营同学出错概率。
4. 把接入流程文档化，最好形成一套标准“新商家接入清单”。

## 八、最后的感受

这类项目最有意思的地方在于，它从来不是“写一个接口、做一个页面”这么简单。

真正花时间的，往往是把历史结构理顺，把接入模型想清楚，把线上运行方式和后台操作方式全部串成一条完整链路。

技术实现只是其中一层，真正让系统可用的，是下面这些东西一起成立：

- 目录结构清楚
- 页面入口明确
- 商家归属稳定
- 配置修改能生效
- 线上部署能复现
- 出问题时能定位

这次改造做完之后，我对这个项目最大的感觉不是“功能又多了一个”，而是：

> 它终于从一个能跑的开发中项目，往一个能真正交付出去的系统，挪近了一步。
