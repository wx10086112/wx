# 微信团购商城 — 完整项目文档

> 基于若依框架(RuoYi-Vue v3.8.9) + 微信小程序整合的本地生活团购商城系统。
> 最后更新：2026-05-25

---

## 一、项目概述

### 1.1 系统定位

本地生活团购商城，类似美团/大众点评的到店团购模式。消费者在 C 端小程序购买团购套餐，到店后由商家扫码或手动核销完成消费。

### 1.2 技术栈

| 层级 | 技术 |
|------|------|
| 后端框架 | Spring Boot 2.5.15 + MyBatis + RuoYi v3.8.9 |
| Java 版本 | Java 8 |
| 构建工具 | Maven 多模块 |
| 数据库 | MySQL (localhost:3306/ruoyi-cs, root/123456) |
| 缓存 | Redis (localhost:6300, 无密码) |
| 微信 SDK | WxJava 4.7.0 |
| 后台前端 | Vue 2.6 + Element UI 2.15 + ECharts 5.4 |
| C 端小程序 | 原生微信小程序；每个商家配置独立 C 端 AppID |
| 商家端小程序 | 原生微信小程序；每个商家配置独立商家端 AppID |

### 1.3 四端架构

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  C 端小程序   │  │ 商家端小程序  │  │  运营后台     │  │  后端服务     │
│  (wx_app)    │  │(merchant_app)│  │ (ruoyi-ui)   │  │(ruoyi-vue-   │
│              │  │              │  │              │  │ wxmini-main) │
│ 消费者使用    │  │ 商家/店员使用  │  │ 平台运营使用   │  │ 提供所有API   │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │                 │                 │                 │
       └─────────────────┴─────────────────┴─────────────────┘
                    HTTP REST API (localhost:8080)
```

| 端 | 目录 | 面向用户 | 主要功能 |
|----|------|---------|---------|
| C 端小程序 | `wx_app/` | 消费者 | 浏览商家/商品、下单支付、查看订单、到店核销 |
| 商家端小程序 | `merchant_app/` | 商家/店员 | 接单、核销、商品管理、门店管理、财务查看 |
| 运营后台 | `ruoyi-ui/` | 平台运营 | 商家审核、订单管理、财务管理、数据分析 |
| 后端服务 | `ruoyi-vue-wxmini-main/` | — | 所有 API 服务、数据库、微信对接 |

### 1.4 多商家双小程序模型

本系统不是所有商家共用同一个微信小程序。真实 SaaS 模型是：**每个商家都有两套独立微信小程序**。

| 小程序 | 面向对象 | 用途 | 商家表配置 |
|------|------|------|------|
| C 端小程序 | 消费者 | 用户访问该商家的商品/团购、下单、支付、查看核销码 | `c_mini_app_id` / `c_mini_app_secret` |
| 商家端小程序 | 商家/店员 | 商家自己上架商品、管理订单、扫码/手动核销、查看结算 | `m_mini_app_id` / `m_mini_app_secret` |

核心规则：

- 一个商家对应一个 C 端小程序和一个商家端小程序。
- 不同商家的 C 端小程序 AppID 不同，展示的数据也不同。
- 不同商家的商家端小程序 AppID 不同，只能管理自己商家的数据。
- 后端通过小程序 `appid` 识别所属商家，再映射到 `merchant_id` 做数据隔离。
- 总后台负责维护每个商家的两套小程序配置、支付配置、商品、团购活动和结算资料。

### 1.5 分销商层级模型

后续系统支持“超级管理员 → 分销商 → 商家”的多级运营模型。

```text
超级管理员 SUPER_ADMIN
  └── 分销商 DISTRIBUTOR_ADMIN
        └── 商家 MERCHANT_ADMIN / MERCHANT_STAFF
```

| 角色 | 数据范围 | 说明 |
|------|------|------|
| 超级管理员 | 全平台 | 管理所有分销商、商家、订单、团购、结算 |
| 分销商 | 自己名下商家 | 管理自己区域/渠道下的商家，不能查看平级分销商 |
| 商家 | 自己商家 | 只能管理自己的商品、团购、订单、核销、结算 |

超级管理员可以切换为任意分销商视角；分销商不能切换身份。

### 2.3 鉴权体系

项目有两套独立的鉴权体系：

**管理后台鉴权 (若依原生)**
- 请求头: `Authorization: Bearer {token}`
- 路径: 除 `/wxmini/**` 外的所有接口

**微信小程序鉴权**
- 请求头: `Wx-Authorization`
- C 端格式: 原始 token 字符串（无 Bearer 前缀）
- 商家端格式: `Bearer {token}`
- 过滤器: `WxMiniJwtFilter`
- 上下文: `WxMiniUserContext` (ThreadLocal)
- 多商家隔离：C 端登录根据当前小程序 AppID 匹配 `merchant.c_mini_app_id`；商家端登录根据当前小程序 AppID 匹配 `merchant.m_mini_app_id`。

**白名单路径**（不需要 token）：
- `GET /wxmini/login`
- `POST /wxmini/login/quick`
- `POST /wxmini/user/phone/bind`
- `GET /wxmini/template/config`

### 3.3 金额约定

所有金额字段以**分**（整数）存储。前端展示时除以 100 转为元。示例：`19800` → `¥198.00`。

### 3.4 商品与团购关系

团购不是商家主表上的固定开关，而是商品的营销归属。

| 表/字段 | 规则 |
|------|------|
| `groupon_activity` | 按商家创建团购促销活动 |
| `product.groupon_id` | 可为空；为空表示普通商品，不为空表示团购商品 |
| `product.merchant_id` | 必须与关联的 `groupon_activity.merchant_id` 一致 |

查询规则：

- 普通商品：`product.groupon_id IS NULL`
- 团购商品：`product.groupon_id IS NOT NULL`
- C 端团购列表只返回已上架商品、进行中的活动、且未过期的数据。
- 商家没有团购时，不需要特殊字段；查询结果为空即可。

### 4.5 C 端订单状态机

```
                ┌─────────────┐
                │ PENDING_PAY │  用户下单后
                │   (待支付)    │
                └──────┬──────┘
           ┌───────────┼───────────┐
           ▼           ▼           ▼
     ┌──────────┐ ┌───────────┐ ┌──────────┐
     │CANCELLED │ │PAID_UNUSED│ │ REFUNDING│
     │  (已取消) │ │  (待使用)  │ │  (退款中) │
     └──────────┘ └─────┬─────┘ └─────┬────┘
                        ▼             ▼
                  ┌───────────┐ ┌──────────┐
                  │  USED_    │ │ REFUNDED │
                  │ COMPLETED │ │  (已退款) │
                  │  (已完成)  │ └──────────┘
                  └───────────┘
                        │
                  ┌──────────┐
                  │  CLOSED  │  超时未支付自动关闭
                  │  (已关闭) │
                  └──────────┘
```

### 4.7 支付流程

```
用户确认订单
    ↓
POST /wxmini/order/create → 创建订单
    ↓
POST /wxmini/pay/order/create → 获取微信支付参数
    ↓
wx.requestPayment(payParams) → 调起微信支付
    ↓
支付成功 → 后端收到微信回调 → 更新订单状态为 PAID_UNUSED
    ↓
前端自动请求订阅消息授权
```

后端未就绪时，前端自动降级为模拟支付（直接更新订单状态）。

### 5.6 扫码核销端到端流程

```
C 端用户                    商家端                      后端
   │                         │                          │
   │ 支付成功 → 订单状态      │                          │
   │ PAID_UNUSED              │                          │
   │ 系统生成 writeOffCode    │                          │
   │ = "LY8012"              │                          │
   │                         │                          │
   │ Canvas 生成二维码 ───────→│                          │
   │ 二维码内容 = "LY8012"    │                          │
   │                         │                          │
   │ 到店出示二维码           │                          │
   │ ────────────────────────→│ wx.scanCode()            │
   │                         │ 读取结果 = "LY8012"       │
   │                         │                          │
   │                         │ POST /write-off/LY8012 ──→│
   │                         │                          │ 校验订单状态
   │                         │                          │ 校验有效期
   │                         │                          │ 更新为 COMPLETED
   │                         │                          │
   │                         │←──── { success: true } ──│
   │                         │ toast "核销成功"           │
   │                         │                          │
   │←── C 端下次刷新订单 ─────│                          │
   │     状态变为 COMPLETED   │                          │
```

**后端核销校验清单**:

| 校验项 | 失败原因 |
|--------|---------|
| 核销码对应订单是否存在 | "未找到对应订单" |
| 订单状态是否为 `PENDING_VERIFY` | "该订单已核销完成" / "当前订单状态不可核销" |
| 团购券是否在有效期内 | "团购券已过有效期" |

### 5.7 商家端响应解析差异

商家端的响应解析与 C 端不同：

| 对比项 | C 端 (wx_app) | 商家端 (merchant_app) |
|--------|---------------|----------------------|
| API 前缀 | `/wxmini/` | `/wxmini/merchant-mini/` |
| Token 格式 | 原始 token（无 Bearer） | `Bearer {token}` |
| Token 存储 key | `token` | `merchantToken` |
| 响应解析 | 取整个 `{code, msg, data}` | 直接取 `data` 字段 |
| 订单状态 | PENDING_PAY → PAID_UNUSED → USED_COMPLETED | PENDING_ACCEPT → ... → COMPLETED |

| `GET` | `/mall/groupon/list` | 团购促销活动列表 |
| `GET` | `/mall/groupon/{id}` | 团购促销活动详情 |
| `POST` | `/mall/groupon` | 新增团购促销活动 |
| `PUT` | `/mall/groupon` | 编辑团购促销活动 |
| `DELETE` | `/mall/groupon/{ids}` | 删除团购促销活动 |
| `PUT` | `/mall/groupon/status` | 团购促销活动上下架 |
| `GET` | `/mall/groupon/options?merchantId={merchantId}` | 指定商家的可选团购活动 |
| `POST` | `/mall/groupon/image/upload` | 上传团购活动封面/海报/详情图 |
| `GET` | `/mall/groupon/product/list?grouponId={grouponId}` | 查询活动关联商品 |
| `POST` | `/mall/groupon/product/bind` | 绑定商品到团购活动 |
| `POST` | `/mall/groupon/product/unbind` | 解绑团购活动商品 |

运营后台保存规则：

- 总后台创建商品或团购活动时必须明确 `merchantId`。
- `product.groupon_id` 可以为空；为空表示普通商品，不为空表示团购商品。
- 绑定团购活动时，后端必须校验商品和活动属于同一个商家。
- 团购活动图片上传到 `merchant_images/{merchantId}/groupon/{grouponId}/`；未保存活动时可先进入 `merchant_images/{merchantId}/groupon/temp/{token}/`。
- 商品图片上传到 `merchant_images/{merchantId}/product/{productId}/`。
- 上传接口返回 URL、文件名和相对路径；数据库保存 URL。

## 七、端到端业务流程

### 7.1 消费者购买流程

```
进入小程序 → 浏览首页 → 搜索/分类 → 查看商家详情
    → 查看商品详情 → 加入购物车/立即购买
    → 确认订单(选择数量/优惠券) → 提交订单
    → 微信支付 → 支付成功 → 查看订单(核销码+二维码)
    → 到店出示二维码 → 商家扫码核销 → 订单完成
    → 评价订单
```

### 7.2 商家运营流程

```
商家登录 → 查看工作台(待接单/待核销/销售额)
    → 订单管理: 接单 → 发货 → 确认送达
    → 核销管理: 扫码/手动核销团购券
    → 商品管理: 上架/下架/编辑商品
    → 门店设置: 修改门店信息
    → 员工管理: 添加/编辑/分配权限
    → 财务: 查看收入/申请提现
```

### 7.3 平台运营流程

```
运营登录后台 → 审核商家入驻申请
    → 管理商家列表/商家等级
    → 查看订单/处理异常/售后
    → 财务管理: 平台收益/商家分账/提现审批
    → 数据分析: 销售排行/订单统计
```

### 7.4 分销商运营流程

```
超级管理员登录后台
    → 分销商管理: 新增/编辑/禁用/重置密码
    → 切换为某个分销商
    → 查看该分销商名下商家、订单、团购、结算
    → 退出分销商视角，返回超级管理员

分销商登录后台
    → 查看自己名下商家
    → 管理自己名下商家的商品、团购、订单、结算
    → 不能查看其他分销商和其他分销商下的商家
```
